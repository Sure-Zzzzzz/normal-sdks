# 旧租户模型到当前商业授权模型的迁移边界

旧 `smart_license_*` 表族以tenant及旧JWS协议为事实源。当前 `license_*` 表族以签发方、客户、产品、授权、对象资格和商业期限为事实源，采用协议2，两者领域模型不兼容。

## 独立新库

不提供旧租户模型的原地DDL或逐行自动转换。新部署使用独立数据库和 `01_schema.sql` 的23张表，不与旧表共库混跑；新库初始化脚本含DROP，只能用于经确认可丢弃的目标库。

新授权根据已确认商业依据登记客户、产品、模型、期限与真实对象绑定，再通过受控签发生成协议2文件。不能从旧tenant推造新客户归属，也不能仅变更协议版本字段使旧文件进入新信任域。

## 旧库归档

停止旧部署的签发写入后，保留旧库、历史文件、公钥绑定、吊销事实与验签规则的受控归档；先核对完整备份和恢复能力，不默认删除旧库。

已交付旧文件的处置由原协议及商业约定决定。当前Verifier不自动降级接受旧协议，当前吊销表也不自动回填旧文件。需要撤回旧文件时，按原验证端支持的规则执行，不能声称新库的吊销会自动撤回旧副本。

## 当前模型的增量升级

已经采用 `license_*` 的库不走上述断代迁移。先备份、停止自己的写入，再按当前实体与 `01_schema.sql` 的结构差异执行数据保留迁移：

- activation_id由冻结Base64URL载荷派生，按02_signing_operation_activation.sql回填；不改冻结字节、签名或状态。
- 缺失商业期限按03_grant_validity_migration.md恢复已确认事实，重签不能因迁移时间延长商业期限。
- 履约去重台账按04_add_fulfillment_grant.sql建立；历史多授权或断裂关联停止并人工核对，不能任取一条。
- 保留签名档案ACTIVE唯一约束、RETIRED公钥历史、任务执行代数及不可撤回吊销事实。

运行时使用结构校验及实际业务回读确认迁移。ddl-auto=update不回填商业事实，不作为升级成功证明。
