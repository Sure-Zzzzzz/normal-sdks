# DDL 执行说明

> 严重警告：`schema.sql` 会先执行 `DROP TABLE IF EXISTS`，删除同名表及全部数据。该脚本仅用于首次安装或确认可销毁的环境；生产环境已有表时禁止重复执行。

## 前提

- MySQL 5.7 或更高版本。
- InnoDB 存储引擎。
- 数据库和连接使用 `utf8mb4`。

## 执行顺序

全新安装执行 `schema.sql`（13 张表：客户/联系人/商机/目录/报价/版本/行/订单/订单行/履约项/消费者注册表/幂等/审计）。已有 1.0.0 数据库必须执行对应的版本迁移脚本，不得用基线脚本覆盖数据。

starter 不自动建表、不自动执行 DDL，也不集成 Flyway 或 Liquibase。部署前必须由数据库变更流程手动执行脚本。

本版本使用基线脚本中的固定表名，不提供表名配置。部署时选择目标数据库，不通过重命名表来隔离不同应用。

## 升级

从 1.0.0 升级到 1.1.0 时，先备份并暂停 CRM 写入，再执行 [1.0.0-to-1.1.0.sql](migration/1.0.0-to-1.1.0.sql)。该脚本只创建商机表、补充报价商机关联列和索引，使用信息架构检查避免重复添加，不删除已有数据。执行后核对表结构和索引，再部署 1.1.0。

`migration/` 目录中的订单展示态核对与修复 SQL 仅用于按明确订单范围更正履约派生态，不改表结构，也不自动执行；执行前须备份、暂停目标订单写入并按 [修复说明](migration/README.md) 完成核对与复核。初始化 `schema.sql` 不得替代结构升级或数据修复。

## 与消费范式的关系

本 DDL 与身份协作底座无外键关联：owner 列（`iam:{subjectId}` 人员 / `aksk:{clientId}` 服务凭证）由 resource-server 验证链派生；消费者注册表的 `consumer_id` 必须与其 AKP 的 clientId 一致（登记时核验），这是履约回写授权（派发归属等值）的依据。
