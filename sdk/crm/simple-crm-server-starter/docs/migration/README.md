# 版本迁移

CRM 1.1.0 提供从 1.0.0 数据库到当前结构的显式升级脚本。本目录同时承载**事实修复脚本**：按明确范围修正存量数据与服务端派生逻辑的偏差，每套脚本含只读核对与带锁修复两步。

## 1.0.0 到 1.1.0

`1.0.0-to-1.1.0.sql` 是一次性结构升级脚本，适用于 1.0.0 的 `schema.sql`。执行前备份目标数据库并暂停 CRM 写入；脚本创建 `crm_opportunity`，为 `crm_quotation` 增加 `opportunity_id` 列和索引，不删除任何业务数据。脚本执行后核对商机表、报价列及索引均存在，再启动 1.1.0 服务。

# 订单履约展示态修复

订单的 `display_state` 是交付事实的派生态：无完成项为 `pending_fulfillment`，部分完成为 `partially_fulfilled`，全部完成为 `fulfilled`。正常回写和人工重置在同一事务内重算；幂等重放只读取首次结果，不校正或修改当前订单。历史偏差需要按明确订单范围执行此修复，不在启动、查询或重放请求中自动回填。

此目录的脚本仅更正订单展示态，并在实际变化时递增一次订单聚合版本、更新变更时间。交付项、结果、水位、报价快照和业务审计均不改动；`closed`、`change_in_progress` 状态不进入履约派生态修复。

执行顺序固定如下：

1. 确认目标数据库，备份目标订单原有 `display_state`、`aggregate_version`、`updated_at`，记录操作工单与执行人。
2. 将 [只读核对脚本](order-display-state.preview.sql) 的示例替换为待修复订单标识并执行，逐项核对交付事实与派生态，确认确有偏差。
3. 协调暂停目标订单的履约回写、人工重置及订单治理写入，直至修复和复核结束。旧服务可能没有订单锁，不能仅依赖脚本加锁与其并行运行。
4. 在新数据库连接中，将 [修复脚本](order-display-state.repair.sql) 的示例替换为完全相同的订单范围后执行。脚本按订单、交付项顺序加锁，使用 `READ COMMITTED` 当前事实计算。任何范围订单不存在时，整批更新数为零；此时先解决范围错误再使用新连接重跑。任一语句失败时立即执行 `ROLLBACK` 并断开连接，禁止忽略错误继续提交。
5. 核对 `expected_orders = found_orders` 与 `repaired_orders`，重跑只读脚本确认派生态，再恢复写入。保存修复前后结果作为运维记录；脚本不伪造一次履约领域动作或重复业务审计。

修复脚本只更新范围内有差异的订单；相同范围重复执行不再次增加版本。禁止删除范围条件、从全表生成范围、使用业务初始化 `schema.sql` 代替修复，或者修改交付事实以迁就旧展示态。
