# 精确策略域（v1 三元组）

限流管理最早的策略形态：一条策略 = 在哪个服务（serviceCode）的哪个资源（resourceCode）上，对哪个主体（subject）配一组时间窗口。表结构见 [schema](../schema.sql)，端点契约见 [openapi](../openapi.yaml)。

## 表关系

```
smart_redis_limiter_policy          策略主表（三元组唯一）
        ↓ 1:N（外键 policy_id，级联删除）
smart_redis_limiter_policy_limit    窗口配置表（一至十六档）
smart_redis_limiter_policy_revision 服务级版本表（独立，与类型化域共用）
```

## 三元组身份

- `service_code` / `resource_code` / `subject` 三列均 `utf8mb4_bin`（区分大小写），组合唯一（`uk_smart_limiter_policy_identity`）——同一三元组只允许一条策略，重复创建返回冲突。
- `subject` 是被限流的稳定对象标识（用户 ID、IP、固定值 `*` 等），语义由调用方约定，服务端不做格式解释。
- 身份三字段创建后不可改：改变归属须删除重建。

## 窗口（limits）

- 每档 = `limit_count`（阈值）+ `limit_window` + `limit_unit`（SECOND/MINUTE/HOUR/DAY），一策略 1–16 档，`sort_order` 决定展示顺序。
- `window_seconds` 由服务层写入前计算（window × unit 标准化秒数），策略内唯一（`uk_..._window_seconds`）——同一策略不允许两个等效时间窗口；更新为整体替换，不做部分合并。
- 引擎语义：多档同时生效，任一档超限即拒绝。

## 乐观锁与 revision

- 策略行带 `row_version` 乐观锁：更新/启停/删除必须携带 `expectedRowVersion`，不匹配即 409；并发方先提交后，后到方必须重读，不自动覆盖。
- `smart_redis_limiter_policy_revision` 是服务级版本行（主键即 serviceCode）：每次策略变更后递增，运行端通过 HTTP 快照的 ETag/revision 感知变化，不直接访问本表。v1 精确域与 v2 类型化域共用这张 revision 表（同服务编码只属一种协议模式）。

## 快照下发

运行端拉取 `GET /v1/policy/snapshot?serviceCode=...`：按 `service_code + enabled` 过滤后有序返回全部启用策略。条件请求携带 `If-None-Match`，版本未变返回 304（304 查询快路径：先以 revision 单行拼 ETag 预判，不触发全量策略查询，见 [目录与快照域](目录与快照域.md)）。
