# Envoy 动态路由

本文描述 adaptor starter 与 Envoy 的目标语义。当前 adaptor 1.0.0 已生成 CDS/EDS/RDS/LDS 静态快照并提供 ADS/SotW gRPC，接收 ACK/NACK；由部署运行目录启动的 Envoy 做真实数据面联调验收。部署运行目录不实现 xDS。

## 输入

Adaptor 从 IAM 的 Portal 可信应用路由投影得到已排除有效内置应用后的可信应用登记，校验后通过 xDS（控制面向 Envoy 下发配置的标准接口）v3 ADS/SotW gRPC 发布完整快照。有效内置分类遵循 IAM 的 `TrustedApplicationBuiltInResolver`（数据库 `built_in=true` 或命中引导内置清单）；Adaptor 不重复推断，也不为 AKSK 生成动态路由。每个动态应用只有一个业务 Nginx origin，页面和 API 路由共用它。快照至少包含 `catalogRevision`、`snapshotVersion`、页面/静态资源路由、API 路由、HTTP 上游 Host、EDS 固定 IP、稳定摘要和生成时间；不包含凭据、用户 Cookie、Token、私钥、完整 Query、请求 Body 或业务数据。

## 为什么仍需路由登记

业务 Nginx 自闭环，指它负责自己的静态页面、API 入口及内部服务分发；不代表统一入口能自动知道某条浏览器路径属于哪个业务。浏览器访问的仍是同一个 IAM 域名，IAM Nginx 只按平台保留路径与通用动态入口分界，不维护逐业务应用连接。Envoy 收到动态请求后，必须用 IAM 发布的路径目录找到应用，再把请求送到该应用唯一的 Nginx origin。

IAM 保存的是统一入口所需的最小映射，不是业务内部拓扑：

| 字段 | 作用 | 是否参与机器转发 |
| --- | --- | --- |
| `routePrefix` | 应用页面和静态资源的公共路径前缀，例如 `/app/example` | 是；匹配后原路径转发 |
| `entry` | Portal 打开的初始文档路径，例如 `/app/example/index.html`；必须等于或位于 `routePrefix` 下 | 否；不另建路由，也不改写路径 |
| `apiBase` | API 的公共路径前缀，例如 `/api/example`；它不是 API 服务地址 | 是；匹配后原路径转发 |
| `targetOrigin` | 页面与 API 共用的业务 Nginx HTTP origin，例如 `http://example-nginx:80` | 是；所有该应用路由共用 |

例如浏览器请求 `/app/example/index.html` 时，IAM Nginx 将未保留的动态页面路径交给 Envoy；Envoy 按 `routePrefix` 命中示例应用，并把原路径转到 `http://example-nginx:80/app/example/index.html`。请求 `/api/example/v1/items` 时，Envoy 按 `apiBase` 命中同一应用，仍转到 `http://example-nginx:80/api/example/v1/items`。业务 Nginx 随后自己提供静态文件或把 API 转给内部服务。IAM/Envoy 不记录业务 Nginx 后面的容器、端口或路径，也不拆出第二个 API origin。

如果删掉 `apiBase`，当 API 使用 `/api/example/**` 而页面使用 `/app/example/**` 时，Envoy 无法仅凭页面前缀判断 API 路径归属；如果删掉 `targetOrigin`，共享域名入口又没有信息可把命中的路径送到哪台业务 Nginx。两个字段解决不同问题，均不代表业务拆成了两个服务。

## 路径规则

IAM Nginx 位于 Envoy 之前。平台保留的 `/`、Portal 壳、`/app/iam/**`、`/iam/**` 和 `/oauth2/**` 不进入本文件定义的 xDS 路由；它们由 IAM Nginx/IAM Server 自闭环。AKSK 等内置应用的固定页面/API 前缀同样由 IAM Nginx 直接转发，不进入 xDS；AKSK 的旧 `/admin/**` 仅在 console 形态下使用独立固定映射。即使 IAM 或 AKSK 作为可信应用记录出现在 Portal 目录中，也不因此生成 Envoy 路由。本文件只描述业务可信应用的页面、静态资源和 API 路由。

IAM Nginx 只维护平台固定入口和一个通用业务入口，不逐个登记应用路径或应用连接。未命中平台固定入口的业务页面/API 请求交给 Envoy；Envoy 再按动态目录中的 `routePrefix` 或 `apiBase` 决定应用归属。新增业务不需要为 IAM Nginx 添加逐应用 location 或连接配置。

- 统一入口前缀原样使用 IAM 投影的 `routePrefix`，不按 applicationCode 重算；`/micro/{code}` 只可能是用户态 Portal 的历史内置路径，不属于本文件的动态机器目录输入，动态应用通常使用 `/app/{code}`。
- 页面和静态资源请求保留 `routePrefix`，转发到 `targetOrigin` 的同路径；`entry` 仅是公共文档入口，不参与 prefix rewrite，应用自己的 Nginx 负责 index fallback 和静态资源。
- `apiBase` 是公共 API 路径，转发到同一个 `targetOrigin` 的同路径；页面和 API 不允许登记两个机器上游。`targetOrigin` 只接受无路径绝对 HTTP origin，HTTPS 地址拒绝整份快照。
- 路径拼接拒绝 `..`、反斜杠、控制字符、非法百分号编码、编码斜杠和重复编码；不同应用按完整 path segment 检查 routePrefix 重叠并使用最长前缀匹配。
- query 在请求转发时保留，但不进入快照摘要、日志或事件；登记值含 query/fragment、userinfo 或非法 host 时由 adaptor 拒绝。

## xDS 更新与确认语义

1. Adaptor 对规范化、稳定排序后的目录计算 `snapshotVersion` 并构建包含 CDS、EDS、RDS、LDS 的完整候选快照。
2. starter 将候选快照写入 Control Plane cache；ADS/SotW server 按 Envoy 当前订阅的资源类型返回响应。starter 不保证跨 CDS、EDS、RDS、LDS 的事务式分阶段提交顺序。
3. 每个 xDS 响应的 nonce 仅关联到产生该响应的 stream、资源类型和快照版本。ACK 只能在同一个 ADS stream 内累计；ACK 不能跨 Envoy stream 拼接。
4. 单个 stream 对当前最新版本的四类资源全部 ACK 后，starter 更新本地已应用状态并产生 `SNAPSHOT_APPLIED`。当前 readiness 表示至少一个 ADS stream 完整确认了最新快照，不表示所有 Envoy 副本都已收敛。
5. NACK 会使对应 stream 的该版本确认失败，并忽略该 stream 对同版本的后续 ACK；Control Plane cache 不会自动回滚。Envoy 对被拒绝的资源类型保留其此前接受的配置，其他类型可能已分别接受新版本，因此多资源类型更新不是事务。后续完整版本被单个 stream ACK 后，才恢复当前 readiness。
6. 正常关闭、异常关闭和 RPC 取消都会清除 stream 的 nonce 与 ACK 状态。Adaptor 关闭时会结束仍存活的长连接 ADS stream，等待控制面服务在限定时间内终止，再清空本地状态。部署运行目录只负责把 adaptor xDS 端口接入 Envoy，不改变该状态机。

EDS 只包含解析通过策略的 IP，Envoy 不使用 `STRICT_DNS`。Host/`:authority` 使用 `targetOrigin` 登记主机；Gateway upstream 固定为 HTTP，不设置 SNI 或 TLS transport socket。DNS 重新解析、地址策略和 IP 变化只在下一次 adaptor 同步并重新校验后生效。

## 多副本和失败响应

所有 adaptor 副本使用同一目录和策略；同一 revision 和输入生成相同摘要。副本允许在同步周期内短暂落后，不以单副本内存状态宣称全局最新。没有有效快照或 `maxStale` 到期时返回 503；未命中 routePrefix 返回 404；不把 IAM 401/403、目标拒绝或上游详情写进响应体。正常同步发现应用禁用/删除时，下一份成功快照立即撤除旧路由。

Gateway readiness 只表示进程、目录快照状态及至少一个 xDS stream 对最新快照的完整确认，不主动访问任意业务 URL，也不能代表所有 Envoy 副本均已收敛。多 Envoy 部署必须逐实例检查数据面 readiness。业务上游健康检查只有在部署运行目录对明确的无副作用路径单独配置时才启用，不能把业务健康伪装成 IAM 健康。
