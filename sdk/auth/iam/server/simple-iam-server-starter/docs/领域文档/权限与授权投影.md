# 权限与授权投影

IAM Server 权限域：RBAC 基础之上，应用权限清单 → 角色授权规则 → 用户授权投影的三层结构与触发语义。模块总览与端点索引见根 [README](../../README.md)。

## 统一授权投影（清单 → 规则 → 投影）

应用授权走三层结构，权限码全局命名空间（`iam:*`、`aksk:*`、`kms:*` 等，应用前缀自治）：

```
iam_application_permission_manifest   应用申报自己的码空间（事实源）
        ↓ 约束
iam_role_authorization_rule           角色 × 应用 = 权限集合（投影计算源）
        ↓ 并集聚合
iam_application_authorization         用户投影（Access Token / 验证端点的授权依据）
```

三张表的权限 JSON 落地形态（均为 JSON 字符串数组；注意以下是**数据库列名**形态，PUT 请求体字段无 `Json` 后缀，见下文「业务方上报指引」）：

**① `iam_application_permission_manifest`** — 应用权限清单（申报制，`PUT /iam/admin/trusted-applications/{id}/permission-manifest`）：

```json
{
  "rolesJson":          ["iam_admin", "iam_user"],
  "pagePermissionsJson": ["iam:user:page", "iam:role:page",
                          "iam:message:page", "iam:trusted-application:page",
                          "iam:department:page", "iam:user-group:page",
                          "iam:dashboard:page"],
  "apiPermissionsJson":  ["iam:user:api", "iam:role:api", "iam:permission:api",
                          "iam:message:api", "iam:trusted-application:api",
                          "iam:department:api", "iam:user-group:api",
                          "iam:dashboard:api", "iam:session:api"]
}
```

`manifestVersion` 服务端单调递增；`manifestDigest` 为各列表（角色 / 页面 / 接口 / DATA 资源）排序去重后规范化 JSON 的 SHA-256。上例是 IAM 应用引导基础清单（7 PAGE + 9 API + 2 角色）；基础 DATA 资源为 `iam:user`（动作 read / write，维度 departmentId）：

```json
"dataResourcesJson": [
  {"resource": "iam:user", "actions": ["read", "write"], "dimensions": ["departmentId"]}
]
```

1.3.2 的增量核对另并入下文受委托角色治理的 8 个 API 码和 5 个 DATA 资源。因此全新安装的默认 IAM 清单为 **2 角色、7 PAGE、17 API、6 DATA 资源**。存量部署保留定制声明，只增量补齐本版治理声明，不保证存量总数与默认总数相同。内置 `iam_admin` 的受管规则也补齐新增 API 与对应 DATA 全量授权，其他角色不会自动获得这些权限。

**② `iam_role_authorization_rule`** — 角色应用授权规则（`(role_id, application_id)` 唯一，`GET / PUT / DELETE /iam/admin/roles/{roleId}/authorization-rules/{applicationId}`）：

```json
{
  "pagePermissionsJson": ["iam:user:page", "iam:role:page"],
  "apiPermissionsJson":  ["iam:user:api", "iam:role:api"],
  "dataGrantTemplateJson": {
    "protocol": "simple-data-permission", "version": "1.0",
    "grants": [{"resource": "iam:user", "actions": ["read"], "all": false,
                "constraints": [{"dimension": "departmentId", "operator": "IN", "values": ["1"]}]}]
  }
}
```

page / api 权限码与 DATA 模板均必须是该应用当前清单的子集：码 ⊆ 清单码表；模板每条 grant 的 resource ⊆ 清单 DATA 资源、action ⊆ 资源申报动作集、constraint.dimension ⊆ 资源申报维度集——越界即拒（`APPLICATION_AUTHORIZATION_002`）。`dataGrantTemplateJson` 为 `null` 表示该角色无数据授权。引导自动为 `iam_admin` 种入全量规则（= 清单复制 + `iam:user` all=true 模板）。

**③ `iam_application_authorization`** — 用户授权投影：

```json
{
  "rolesJson":            ["iam_admin"],
  "pagePermissionsJson":  ["iam:user:page", "iam:role:page"],
  "apiPermissionsJson":   ["iam:user:api", "iam:role:api"],
  "dataGrantDocumentJson": {
    "protocol": "simple-data-permission", "version": "1.0",
    "grants": [{"resource": "iam:user", "actions": ["read", "write"], "all": true, "constraints": []}]
  }
}
```

投影内容 = 用户当前全部角色在该应用下规则的**并集**（page / api 各自并集，无规则即空集）；DATA 同语义——投影 `dataGrantDocumentJson` = 全部角色规则模板的 grants 并集（拼接后规范化，DNF OR），无任何模板即 `null`（资源端失败关闭）。**一切权限经角色：DATA 权威通道为角色规则模板并集投影，管理面手工授权里的 DATA 编辑是重算前的临时精调，角色一变即被规则并集刷新。** `admitted` 是准入位、`status` 是授权生命周期位、`authorizationVersion` 每次重算 +1，`manifestVersion` / `manifestDigest` 记录投影所依据的清单版本。

**投影重算触发事件（五类）**：

| # | 事件 | 重算范围 |
|---|---|---|
| 1 | 准入授予 | 该用户该应用重算并置 `admitted=1`（幂等） |
| 2 | 用户角色分配 / 撤销、部门角色挂载 / 撤销、用户迁部门、角色删除 | 按变化前后有效角色重算受影响用户；已有生效投影的应用 ∪ 当前角色规则覆盖的应用，新覆盖建投影（`admitted=1`），不再覆盖的收缩为空权限集（`admitted` 不变）。角色删除级联删除其全部规则并对成员逐个触发重算 |
| 3 | 角色规则新增 / 修改 / 删除 | 持有该角色的全部用户重算该应用（无投影者新建，`admitted=1`） |
| 4 | 应用清单替换 | 规则覆盖到的用户全量重算；其余存量投影仅同步 `manifestVersion` / `manifestDigest` |
| 5 | 准入撤销 | `admitted=0` + `revokedAt`，内容保留用于追溯（幂等） |

**语义约定**：

- 例行重算（事件 2/3/4）只改权限内容与 `authorizationVersion`，不翻转既有投影的 `admitted`；准入位归准入动作（事件 1/5）管理
- 管理面手工 PUT 用户应用授权仍是直接写入口（适用无规则应用的手工授权）；其写入内容会被下一次触发事件的重算**覆盖**——配置了规则的应用以规则为准
- 清单收缩（移除码）不会自动改写存量规则，规则中越界码需管理员同步修订；重算按规则原样聚合

## 服务主体受委托角色（1.3.2）

受委托角色是外部服务通过 HTTP 创建、仍进入既有角色与授权投影链的普通 IAM 角色。新增 `iam_open_role_binding` 只记录管理边界与版本，不另存一份用户权限，也不表示 License、商业有效期或产品资格。

### 身份、归属与范围

新治理端点只接受可信来源为 AKSK 的 `SERVICE`（服务）主体。管理员会话、IAM 人员 Access Token 和 `HUMAN`（人员）主体不能代替服务身份。每个请求先检查对 `applicationCode=iam` 的准入，再检查精确 API 码与完整 DATA 授权；旧 `iam:user:api`、`iam:department:api` 不包含新治理权，旧 AKP 不自动扩权。

| API 码 | DATA 资源 | 动作 | 可约束维度 |
|---|---|---|---|
| `iam:open-role:create:api`、`iam:open-role:read:api` | `iam:open-role` | `create,read` | `applicationId,rootDepartmentId` |
| `iam:open-role-rule:read:api`、`iam:open-role-rule:write:api` | `iam:open-role-rule` | `read,write` | `applicationId,rootDepartmentId,openRoleId` |
| `iam:open-department-role:read:api`、`iam:open-department-role:write:api` | `iam:open-department-role` | `read,write` | `applicationId,rootDepartmentId,openRoleId,departmentId` |
| `iam:open-directory:read:api` | `iam:open-directory` | `read` | `rootDepartmentId` |
| `iam:open-application:read:api` | `iam:open-application` | `read` | `applicationId` |

服务归属取已验证身份的 `sourceId/subjectType/subjectId` 三元组，不接受调用方提交 owner。创建后固定一个非内置应用和一个部门根，不能更换归属、应用或根。每个 DATA grant 内条件为 AND，不同 grant 为 OR；不得拼接两条 grant 的应用与根条件来制造新的管理范围。`all=true` 也不绕过服务归属和固定范围。

两份 DATA 文档职责不同：**AKSK 服务授权中的 DATA** 决定该服务能治理哪些 IAM 对象；**目标角色规则中的 `dataGrantTemplate`** 决定最终用户可访问哪些业务数据。规则写权是批准范围内的治理权，不自动限定为服务自身运行权限的子集，但角色规则仍必须符合目标应用当前权限清单。

### 创建、版本与生命周期

`POST /iam/api/roles` 使用调用方 `externalId` UUID 作为创建幂等键，服务端生成稳定 `openRoleId` UUID 与角色编码。相同主体、创建键和规范化内容首次返回 201，重放返回当前角色 200，不重置已有规则或关系；同键不同内容或已删除墓碑返回 409。管理面仍使用内部 `roleId`，不能将它与 `openRoleId` 或创建键混用。

角色详情及规则响应提供强 ETag（HTTP 条件写版本标记），形式为 `"open-role:<openRoleId>:<revision>"`。规则与部门关系写入提交 If-Match：缺失 428、旧版本 412、非法标记 400，不接受弱标记、通配符或列表。规则替换另核对目标清单的 `manifestVersion/manifestDigest`，清单变化返回 409。无变化写入不递增 revision、不重复重算投影或发布变更事件。超时或冲突后先回读当前内容并重算差异，不能取得新标记后盲重发旧内容。

受委托角色禁止个人直接分配、传统全局权限和跨应用规则。服务端开放 API 不提供改名或删除角色入口；管理员仍可在管理面按共同版本和范围约束操作，删除清理角色贡献并保留 `DELETED` 墓碑，原创建键不能复活。有 ACTIVE 委托引用的应用或根不能删除，目标应用也不能改为内置应用，均返回 409。

管理角色详情、总列表、分页、部门挂载角色及用户有效角色均返回只读 `openRoleBinding`，普通角色为 null。摘要包含固定应用、部门根、状态和 revision，用于识别委托边界；列表批量查询摘要，不逐角色回读。管理写入前读取当前详情取得版本，列表摘要不能代替同事务条件写校验。

### 根子树与成员事实

部门关系 GET 返回 `Cache-Control: no-store`，不提供 ETag，也不按 If-None-Match 返回 304。关系的组织归属及调用方 DATA 可独立于角色版本变化，每次必须读取当前完整分页；响应体保留同事务 revision，写入版本标记从角色详情读取。创建的应用/根编号及规则清单版本只接受正数 int64 JSON 整数，小数、指数形式、字符串、布尔值、null 和溢出均返回 400，不做截断或类型转换。

用户仍只继承**直属部门**挂载的角色，父部门角色不会自动递归继承。覆盖客户根及子树时，消费方读取 `GET /iam/api/organization-directories/{rootDepartmentId}/departments` 的完整结果，再逐部门调用 `PUT /iam/api/departments/{departmentId}/roles/{openRoleId}`；不能只挂根就宣称覆盖整家公司。

新增关系须位于当前固定根子树内；已迁出或消失的部门仍允许清理本角色残留关系。部门关系查询只返回当前批准范围内的关系。完整目录包含根，最多 4096 节点、64 层；子树节点或深度、关系及成员祖先链深度超限返回 422，不返回截断成功。环、根的悬空父链等组织结构冲突返回 409。

`GET /iam/api/organization-directories/{rootDepartmentId}/members/{subjectId}` 仅返回最小成员事实；不存在或不在根内统一 404，返回成员也不代表账号可用或产品授权有效，消费方须检查状态和自身资格。组织归属及调用方 DATA 授权可能独立变化，不能用角色 revision 判断它们未变化。归属、revision、目录、成员资格及分页不新增缓存；受委托角色的规则和部门关系变化复用上述投影重算。

IAM 投影收缩不保证将用户 `admitted` 关闭；菜单可见、Token 可签或角色存在均不能代替商业资格判断。有效期、宽限期、机器绑定及失效后的业务拒绝归消费方，IAM 不持有这些业务属性。数据库重建或恢复后，消费方必须暂停自动联动并重新核对主体、应用、根及三权，不能按名称或复用数字编号接管旧状态。

## 业务方上报指引（我该怎么申报权限）

业务应用接入方按顺序回答四个问题，每步一个端点：

| 步骤 | 我要做什么 | 端点与请求体关键字段 |
|---|---|---|
| 1 | 建可信应用（含初始 OAuth 客户端） | `POST /iam/admin/trusted-applications` |
| 2 | 申报本应用全部权限码（清单，全量替换语义） | `PUT /iam/admin/trusted-applications/{applicationId}/permission-manifest`（`roles` / `pagePermissions` / `apiPermissions` / `dataResources`） |
| 3 | 给角色配该应用的码集合 | `PUT /iam/admin/roles/{roleId}/authorization-rules/{applicationId}`（`pagePermissions` / `apiPermissions` / `dataGrantTemplate`） |
| 4 | 给用户准入 | `PUT /iam/admin/users/{subjectId}/application-authorizations/{applicationId}`（`admitted=true`） |

**第 2 步是业务方唯一需要"发明"的东西**——把应用里所有受控权限点一次列全。请求体字段是 `roles` / `pagePermissions` / `apiPermissions` / `dataResources`（无 `Json` 后缀；下文表形态示例中的 `rolesJson` 等带后缀形式是数据库列名，不是请求字段）：

```json
{
  "roles":          ["order_manager", "order_viewer"],
  "pagePermissions": ["order:list:page", "order:detail:page"],
  "apiPermissions":  ["order:read:api", "order:write:api"],
  "dataResources": [
    {"resource": "order", "actions": ["read", "write"], "dimensions": ["region"]}
  ]
}
```

易踩的坑：

- **全量替换**：清单 PUT 是整体覆盖不是增量合并，每次上报必须携带该应用**当前全量**码表；漏写的码从清单消失，存量规则不会自动裁剪，重算仍按规则聚合。管理员须同步修订越界规则，后续写规则时仍校验当前清单；`manifestVersion` 服务端递增，请求不带
- **码前缀自治但不校验**：IAM 只校验非空 / ≤256 字符 / 去重，**不校验码前缀与 applicationCode 一致**——前缀约定（如 `order:*`）靠应用自己守，一旦两个应用申报了同名码，全局命名空间就混了；建议申报前 GET 全部应用清单核对无重名
- **四字段必填可为空数组**：`null` 拒（`APPLICATION_AUTHORIZATION_002`）；不用 DATA 权限就传 `"dataResources": []`
- **角色码进清单供角色规则勾选**：`roles` 是应用自己定义的角色编码（如 `order_manager`），业务方后端用它做应用内鉴权；与 IAM 全局角色（`iam_admin` 等）是两回事
- **DATA 声明是角色规则的上游**：第 3 步角色规则模板里每条 grant 的 `resource` / `action` / `constraint.dimension` 必须 ⊆ 第 2 步 `dataResources` 的申报（各自子集），越界即拒——所以 DATA 资源要**先在清单申报**，规则里才有得选

**验证**：用户走一遍登录拿 Access Token，解 payload 看 `iam_authorization` 投影（`admitted` / `applicationCode` / `roles` / `pagePermissions` / `apiPermissions` / `dataGrantDocument` / `manifestVersion` / `manifestDigest` / `authorizationVersion` 等，见 [OAuth2与令牌验证](OAuth2与令牌验证.md)）；或调 `POST /iam/resource/tokens/verify` 看返回的 `iam_authorization` 字段（同一份投影）。

## 应用注册形态选择（内置 vs 非内置）

注册可信应用时的 `builtIn` 标记是一次**治理决策**，判定标准是"该应用的业务数据该不该归平台管理员无授权可见"，与"是否对外售卖产品"无关：

| | 内置应用 | 非内置（业务）应用 |
|---|---|---|
| 语义 | 平台自身组件，让渡治理权给平台管理员 | 业务数据治理权归业务自己的管理角色 |
| iam_admin 特权（1.3.1 起） | 直接接管全量（PAGE/API/DATA all=true） | **零默认可见**；治理须挂业务自宣告角色（如 kms-admin） |
| 生命周期 | 禁删除 / 禁停用，下线走关闭门户集成 | 可删可停（业务自治） |
| OAuth 客户端 | 强制免授权确认 | 走标准授权确认 |
| 注册入口 | 管理面可标记 + 引导配置清单（编码不可摘除内置标记） | 管理台注册即可 |

**选择口诀**：内置 = 平台组件（iam / aksk / portal 及纯平台级运维台）；非内置 = 业务资源服务（kms / license / crm 等一切承载业务数据的应用）。

**产品售卖形态不改变这个选择**——卖给客户的部署实例中，客户的平台管理员管身份基础设施，客户业务方的密钥等业务数据归业务管理角色，权限边界正是产品化治理卖点；单独售卖的应用（不带本 IAM 部署）更不进内置清单。产品化交付关注的是 manifest 能力目录的完整性与业务管理角色（如 kms-admin）的可交付性，两者均在非内置形态下成立。

**内置判定口径**：`built_in` 列优先、引导配置清单兜底（`TrustedApplicationBuiltInResolver` 单一事实源）。模块默认内置域仅 `iam`；部署方可经引导配置追加（如联调形态追加 `aksk`），追加项与默认项行为一致。

## 平台管理员特权（iam_admin，1.3.1 起特权域=内置应用）

内置角色 `iam_admin` 除管理台进门权（`ROLE_iam_admin`）外还携带平台管理员特权：**特权不落库，是授权解析的兜底**。`loadActiveContext`（Access Token 与验证端点的投影读取）优先返回有效、已准入且能解析的真实授权行；行缺失、无效或权限内容解析失败时，才尝试平台管理员兜底。用户有效角色（个人直挂 ∪ 直属部门挂载）含 `iam_admin`，**且目标应用为内置应用**（`TrustedApplicationBuiltInResolver` 判定：`built_in` 列优先、引导配置清单兜底）时，兜底合成如下上下文，而不是无条件覆盖有效授权行：

- `admitted=true`；roles / pagePermissions / apiPermissions = 该应用**当前清单申报的全量**
- DATA：每种申报资源合成一条 `all=true` 无约束 grant（全量可见，无约束）
- 版本字段按当前清单真值（`authorizationVersion=manifestVersion`）；应用未登记清单时合成空权限集（准入但无码）
- 门户可达列表同样直通：平台管理员可见**全部内置应用**的 Portal 集成

**非内置（业务）应用不走特权（1.3.1）**：`loadActiveContext` 对非内置应用返回授权行结果（无授权行即 null，无清单应用亦然），门户可达列表要求真实授权行——访问业务应用必须显式授权或经业务自宣告角色投影。此为角色边界定案的落地：平台管理员治理平台自身组件，业务数据治理权归业务应用的管理角色。

| 特性 | 语义 |
|---|---|
| 不落特权行 | 应用注册不回填特权；既有角色及投影重算不另写一份特权授权 |
| 即时生效 | 挂 / 摘 `iam_admin` 即时生效（解析时现查角色），无需投影重算；已签发 Access Token 的本地验签快照沿用既有 token 生命周期语义 |
| 清单跟随 | 兜底上下文按当前 manifest 合成全量；真实有效授权行仍优先 |
| 审计纯净 | `iam_application_authorization` 只存真实配置授权，特权不产生行 |
| 降权路径 | 摘除 `iam_admin` 角色（命中最后管理员保护时 409）；单应用撤销对特权不生效（1.3.1 起该语义仅对内置应用成立，非内置应用撤销后按授权行缺失处理） |

管理面 GET 用户应用授权摘要 / 详情按用户是否平台管理员下发 `platformAdmin` 标记。它是展示字段，不代表所有应用均有平台特权，也不是服务端撤销禁令；前端不能据此推断已实现禁用撤销入口。

## 组织与人员同步的 DATA 消费（开放 API `/iam/api/**`）

投影 `dataGrantDocument` 经 AKSK introspect 随授权快照出侧（`VerifiedResourceContext.applicationAuthorization`），由 data-permission 公共组件在开放 API 端点评估执行：

- **码 + DATA 双闸**：端点先过 `@RequireApiPermission` 精确码控（如 `iam:user:api`），再过 `@DataPermissionOperation(resource, action)` 数据范围评估——有码无 DATA 文档即 403（失败关闭）
- **读列表**：计划翻译为部门范围，与请求过滤条件**求交**（`departmentId IN 授权集`，越权数据不出库）；授权集内无可见部门时直接空页
- **读详情 / 写操作**：目标用户（或建用户的目标部门）的 `departmentId` 须完整满足至少一个 grant（同 grant 内约束 AND、grant 间 OR），越界 403
- **失败关闭**：计划不可执行（未知维度、非 `IN` 操作符、无可执行约束、值非法）一律 403，不以放宽解释执行
- 既有部门 CRUD 族（`/iam/api/departments`）纯码控不挂 DATA；1.3.2 的受委托部门角色关系、根目录和成员事实端点则按上文独立 API / DATA 检查，不能套用旧部门族规则
